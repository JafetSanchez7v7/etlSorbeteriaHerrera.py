# Sorbetería Herrera — Technical ETL Documentation (2026)

## Analytics Database Component

## 1. Introduction

This document describes the Extract, Transform, and Load (ETL) process for audit logs generated by the Sorbetería Herrera system. The process transfers audit records stored in MongoDB to a technical data warehouse implemented in SQL Server.

The processed information is organized using a dimensional model to facilitate subsequent analytical queries and OLAP cube development.

## 2. Objective

The objective of the Sorbetería Herrera ETL process is to extract audit data from MongoDB, transform it using Python and libraries such as Pandas, and load the processed data into SQL Server, where the technical data warehouse stores the information for subsequent analysis.

## 3. Scope

The ETL process includes the following activities:

- Extracting audit records from MongoDB.
- Transforming and normalizing the extracted documents using Python and Pandas.
- Preparing data for storage in dimension tables and the fact table.
- Loading data into SQL Server using staging tables and integration operations.
- Updating existing dimension records and inserting new records according to their keys.

This process does not include the creation, configuration, or processing of OLAP cubes, regardless of their storage architecture. These activities belong to a later phase of the project.

The ETL process does not modify the original audit logs stored in MongoDB. Transformations are performed on the extracted data to prepare it for loading into the data warehouse.

## 4. System Requirements

The following components are required to execute the ETL process:

- **Docker:** Builds and runs the ETL container.
- **Docker Compose:** Configures and runs the service through a Compose file.
- **MongoDB:** Stores the API audit records.
- **SQL Server:** Hosts the technical data warehouse.
- **Environment configuration:** Connection parameters supplied through environment variables.
- **Python dependencies:** Pandas, PyMongo, SQLAlchemy, PyODBC, and the other libraries declared in the project's `requirement.txt` file.
- **ODBC driver:** A compatible SQL Server ODBC driver installed in the ETL execution environment.

MongoDB and SQL Server can run as local services or containers, provided that the ETL container can reach both services through their configured connection parameters.

## 5. ETL Workflow

### 5.1. Data Source

The Sorbetería Herrera API uses middleware to intercept incoming HTTP requests. Information is collected from each request's HTTP context, including request details, response information, and exception details when applicable.

The generated audit records are stored as documents in MongoDB using the corresponding MongoDB driver for .NET.

The audit record structure is represented by the `ApiUsageLog` class and its supporting classes: `RequestDetail`, `ResponseDetail`, and `ExceptionDetail`.

```csharp
public class ApiUsageLog
{
    public string? Id { get; set; }
    public string TraceId { get; set; } = string.Empty;
    public DateTime Timestamp { get; set; } = DateTime.UtcNow;
    public string Level { get; set; } = "Information";
    public string Environment { get; set; } = "Development";
    public string? ClientIp { get; set; }
    public string? UserId { get; set; }
    public RequestDetail Request { get; set; } = new();
    public ResponseDetail Response { get; set; } = new();
    public ExceptionDetail? Exception { get; set; }
    public string? UserName { get; set; }
    public string? Rol { get; set; }
    public string? Device { get; set; }
}

public class RequestDetail
{
    public string Method { get; set; } = string.Empty;
    public string Path { get; set; } = string.Empty;
    public string? QueryString { get; set; }
    public string? Payload { get; set; }
}

public class ResponseDetail
{
    public int StatusCode { get; set; }
    public long ElapsedMilliseconds { get; set; }
    public string? Status { get; set; }
}

public class ExceptionDetail
{
    public string Message { get; set; } = string.Empty;
    public string? StackTrace { get; set; }
    public string Source { get; set; } = string.Empty;
}
```

#### Main fields

- `TraceId`: Identifier associated with tracking an HTTP request.
- `Timestamp`: Date and time when the event is recorded.
- `Level` and `Environment`: Log severity level and execution environment.
- `ClientIp`, `UserId`, `UserName`, and `Rol`: Available client or user context.
- `Request`: HTTP method, route, and other request information.
- `Response`: HTTP status code and request processing time.
- `Exception`: Exception message, source, and stack trace when available.

The `Request`, `Response`, and `Exception` objects contain nested structures that must be normalized during Python processing.

### 5.2. Data Extraction

The ETL process uses Python and PyMongo to connect to MongoDB and retrieve documents from the configured audit collection.

The following code extracts the documents and performs initial normalization:

```python
# Retrieve documents without MongoDB's internal identifier.
documentos = list(collection.find({}, {'_id': 0}))

if not documentos:
    print("No documents found in the collection")
    return

# Flatten nested JSON objects.
df_crudo = pd.json_normalize(documentos)

# Normalize column names.
df_crudo.columns = df_crudo.columns.str.replace('.', '_')
```

The `collection.find()` method retrieves documents from the selected collection. The projection `{'_id': 0}` excludes MongoDB's internal identifier from the returned documents.

Next, `pd.json_normalize()` converts the JSON documents into a tabular Pandas DataFrame. Nested objects become columns whose names represent their original hierarchy.

Finally, periods in column names are replaced with underscores to simplify field references during transformation and SQL Server loading.

If the collection contains no documents, the script displays a message and stops the current ETL execution before proceeding to subsequent stages.

### 5.3. Data Transformation

After extraction, the documents are available in memory through the `df_crudo` DataFrame. Separate DataFrames are created to represent the dimensions and fact records in the technical data warehouse.

This stage includes data normalization, handling missing values, data type conversion, and generating identifiers used to relate records across the dimensional model.

#### 5.3.1. Date Dimension Transformation

The date dimension organizes audit records according to when each event occurred. The `timestamp` field is converted to a date-time representation using Pandas.

```python
# Build the date dimension.
df_fecha = pd.DataFrame()

ts = 'Timestamp_original'
df_fecha[ts] = pd.to_datetime(df_crudo['timestamp'])

# Generate the date key in YYYYMMDD format.
df_fecha['Id_Fecha'] = df_fecha[ts].dt.strftime('%Y%m%d')

# Extract date and time attributes.
df_fecha['Anio'] = df_fecha[ts].dt.year
df_fecha['Mes'] = df_fecha[ts].dt.month
df_fecha['Dia'] = df_fecha[ts].dt.day
df_fecha['Hora'] = df_fecha[ts].dt.hour
df_fecha['Minuto'] = df_fecha[ts].dt.minute

# Keep one row per date.
df_fecha = df_fecha.drop_duplicates(subset=['Id_Fecha'])
```

The `Id_Fecha` column is generated in `YYYYMMDD` format and serves as the dimension key. The `Anio`, `Mes`, `Dia`, `Hora`, and `Minuto` attributes support analytical grouping by temporal components.

The `drop_duplicates()` operation removes rows sharing the same date identifier, retaining one row per day.

**Technical consideration:** although the dimension includes hour and minute attributes, its key identifies only the calendar day. If multiple events occur on the same day, only one row for that date is retained. This is appropriate for a daily-grain date dimension, but the key and deduplication strategy must change if the dimension is intended to represent individual minutes or timestamps.

### 5.4. Data Loading

The loading stage transfers transformed data into the SQL Server technical data warehouse. SQLAlchemy provides database integration for Pandas, while PyODBC is used to execute SQL statements directly.

#### 5.4.1. Database Connection Configuration

Connection parameters are supplied through environment variables, keeping configuration separate from the source code.

```python
from sqlalchemy.engine import URL

host, port = SQL_SERVER.split(',', 1)

connection_url = URL.create(
    "mssql+pyodbc",
    username=SQL_USER,
    password=SQL_PASSWORD,
    host=host,
    port=int(port),
    database=SQL_DATABASE,
    query={
        "driver": "ODBC Driver 17 for SQL Server",
        "TrustServerCertificate": "yes"
    }
)

engine = create_engine(connection_url)

conn_str = (
    "DRIVER={ODBC Driver 17 for SQL Server};"
    f"SERVER={SQL_SERVER};"
    f"DATABASE={SQL_DATABASE};"
    f"UID={SQL_USER};"
    f"PWD={SQL_PASSWORD};"
    "TrustServerCertificate=yes;"
)

conn = pyodbc.connect(conn_str)
cursor = conn.cursor()
```

`URL.create()` builds the SQLAlchemy connection URL, and `create_engine()` creates the engine used by Pandas when writing DataFrames to SQL Server.

PyODBC establishes a direct database connection and provides a cursor for executing SQL statements, including `MERGE` operations.

The `TrustServerCertificate=yes` option trusts the server certificate without fully validating it. Its use should be evaluated according to the security requirements of the environment.

#### 5.4.2. Dimension Loading Using Staging Tables and MERGE

The reusable `cargar_dimensiones()` function loads dimension DataFrames into their destination tables. It receives a DataFrame, the destination table name, and the name of the primary key.

A staging table temporarily stores the transformed records before they are integrated into the final dimension.

```python
def cargar_dimensiones(df, destino, pk):
    if df.empty:
        return

    staging_tabla = f"Staging_{destino}"

    df.to_sql(
        staging_tabla,
        con=engine,
        if_exists='replace',
        index=False
    )

    columnas = ", ".join(df.columns)
    valores_source = ", ".join(
        [f"source.{col}" for col in df.columns]
    )

    columnas_a_actualizar = [
        f"target.{col} = source.{col}"
        for col in df.columns
        if col != pk
    ]

    actualizar_sets = ", ".join(columnas_a_actualizar)

    if actualizar_sets:
        match_clause = (
            f"WHEN MATCHED THEN UPDATE SET {actualizar_sets}"
        )
    else:
        match_clause = ""

    merge_query = f"""
        MERGE {destino} AS TARGET
        USING {staging_tabla} AS SOURCE
        ON TARGET.{pk} = SOURCE.{pk}
        {match_clause}
        WHEN NOT MATCHED THEN
            INSERT ({columnas})
            VALUES ({valores_source});
    """

    cursor.execute(merge_query)
    conn.commit()

    print(f"DIMENSION {destino} LOADED")
```

The function performs the following operations:

1. Checks whether the DataFrame contains records.
2. Writes the records to a staging table using `to_sql()`.
3. Builds a `MERGE` statement to compare staging records with the destination dimension.
4. Updates existing records when their primary keys match.
5. Inserts records whose keys do not exist in the destination.
6. Commits the transaction using `conn.commit()`.

The matching condition uses the primary key supplied through the `pk` parameter. This allows existing dimension records to be updated and new records to be inserted.

**Important:** `if_exists='replace'` replaces the staging table, not the final dimension table. The destination dimension is maintained through the `MERGE` operation.

The date dimension is loaded using:

```python
cargar_dimensiones(df_fecha, "Dim_Fecha", "Id_Fecha")
```

This call passes the `df_fecha` DataFrame to the loading function, specifies `Dim_Fecha` as the destination table, and uses `Id_Fecha` as the matching key.

#### 5.4.3. Fact Table Loading

Once the dimension data has been prepared, the ETL process loads the `Fact_ApiLogs` table, which stores audit records and their relationships with the dimensions of the technical data warehouse.

As with dimension loading, a staging table named `Staging_Fact_ApiLogs` is used to temporarily store the transformed records.

```python
# Use a staging table to prepare fact records.
if not df_hechos.empty:
    df_hechos.to_sql(
        "Staging_Fact_ApiLogs",
        con=engine,
        if_exists="replace",
        index=False
    )

    insert_hechos_query = """
        INSERT INTO Fact_ApiLogs (
            TraceId, Level, Environment, ClientIp,
            UserId, UserName, Rol, Device,
            Id_Fecha, Id_Request, Id_Response,
            Id_Excepcion, ElapsedMilliseconds
        )
        SELECT
            source.TraceId, source.Level, source.Environment,
            source.ClientIp, source.UserId, source.UserName,
            source.Rol, source.Device, source.Id_Fecha,
            source.Id_Request, source.Id_Response,
            source.Id_Excepcion, source.ElapsedMilliseconds
        FROM Staging_Fact_ApiLogs AS source
        WHERE NOT EXISTS (
            SELECT 1
            FROM Fact_ApiLogs AS target
            WHERE target.TraceId = source.TraceId
        );
    """

    cursor.execute(insert_hechos_query)
    conn.commit()

print("FACT TABLE LOAD COMPLETED")

cursor.close()
conn.close()

print("ETL process completed")
```

The loading procedure includes the following steps:

1. **Staging preparation:** If `df_hechos` contains records, Pandas writes them to `Staging_Fact_ApiLogs`.
2. **Selective insertion:** An `INSERT INTO ... SELECT` statement transfers records from staging into `Fact_ApiLogs`.
3. **Duplicate prevention:** `WHERE NOT EXISTS` checks whether a record with the same `TraceId` already exists in the destination. Only records with no matching identifier are inserted.
4. **Transaction commit:** `conn.commit()` confirms the database changes.
5. **Resource cleanup:** The PyODBC cursor and connection are closed after loading.

Unlike dimension loading, which uses `MERGE` to insert or update records, the fact-loading logic uses selective insertion. Existing records with a matching `TraceId` are not updated by this code.

**Technical consideration:** this strategy assumes that `TraceId` uniquely identifies each fact record. If multiple valid records can share the same `TraceId`, a suitable business key or unique identifier should be defined. A database uniqueness constraint should also be considered to protect against duplicates during concurrent executions.

### 5.5. ETL Workflow Summary

The documented workflow can be summarized as follows:

1. API middleware records HTTP request and response information.
2. Audit records are stored as documents in MongoDB.
3. Python and PyMongo extract the documents from the configured collection.
4. Pandas normalizes the documents and prepares the DataFrames.
5. Transformed records are written to SQL Server staging tables.
6. Dimension records are integrated using `MERGE`.
7. Fact records are inserted using a `NOT EXISTS` condition.
8. The technical data warehouse becomes available for subsequent analytical operations.

## 6. Environment Configuration

The ETL process uses environment variables to configure its connections to MongoDB and SQL Server. This separates infrastructure settings from the source code.

An `.env.example` file documents the required variables without exposing actual credentials.


| Variable | Description |
|---|---|
| `MONGO_URI` | Connection string used to access MongoDB. |

| `SQL_PASSWORD` | Password associated with the SQL Server login. |

Replace the example values with the appropriate settings for the target environment. The real `.env` file should be excluded from version control whenever it contains credentials.

## 7. Docker Image

The ETL runs inside a container based on Python. The image installs the system dependencies required for Microsoft's ODBC driver and the Python libraries declared in `requirement.txt`.

The `Dockerfile` defines the image and its build instructions.

```dockerfile
FROM python:3.14-slim-bookworm

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
ENV ACCEPT_EULA=Y

WORKDIR /app

# Install system dependencies and configure Microsoft's repository.
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        ca-certificates \
        curl \
        gnupg \
        g++ \
        unixodbc-dev \
    && curl -fsSL https://packages.microsoft.com/keys/microsoft.asc \
        | gpg --dearmor -o /usr/share/keyrings/microsoft-prod.gpg \
    && echo "deb [arch=amd64,arm64 signed-by=/usr/share/keyrings/microsoft-prod.gpg] https://packages.microsoft.com/debian/12/prod bookworm main" \
        > /etc/apt/sources.list.d/microsoft-prod.list \
    && apt-get update \
    && ACCEPT_EULA=Y apt-get install -y --no-install-recommends msodbcsql17 \
    && rm -rf /var/lib/apt/lists/*

# Install Python dependencies.
COPY requirement.txt .
RUN pip install --no-cache-dir -r requirement.txt

# Copy the ETL script.
COPY etl_script.py .

CMD ["python", "-u", "etl_script.py"]
```

The image build process consists of the following stages:

1. Select a Python base image running on Debian Bookworm.
2. Install system dependencies and Microsoft's SQL Server ODBC driver.
3. Copy and install the Python dependencies.
4. Copy the `etl_script.py` file into the image.
5. Configure the default command to execute the ETL process.

`PYTHONUNBUFFERED=1` ensures that output is written without Python's usual buffering, making it easier to monitor container logs.

## 8. Docker Compose Configuration

Docker Compose defines the ETL service, its build configuration, environment variables, and connectivity to services running on the host.

The `compose.yaml` file uses the following configuration:

```yaml
services:
  etl:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: etl_container
    env_file:
      - .env
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

The configuration includes:

- **`build`:** Builds the image from the project's `Dockerfile`.
- **`container_name`:** Sets the container name.
- **`env_file`:** Loads connection variables from `.env`.
- **`extra_hosts`:** Maps `host.docker.internal` to the host gateway in Docker environments that require this configuration.

This setting is useful when MongoDB or SQL Server runs directly on the host machine. If the databases run in other containers, the appropriate Docker networks and service names must be configured instead.

## 9. Running the ETL Process

From the directory containing the Compose file, run:

```bash
docker compose run --build --rm etl
```

The command:

1. Builds or updates the service image.
2. Creates a container to execute the ETL.
3. Runs the command defined in the `Dockerfile`.
4. Removes the container after execution because of the `--rm` option.

Before running the command, ensure that `.env` is correctly configured and that MongoDB and SQL Server are reachable.

The script's output can be used to monitor the reported execution stages. A successful run should also be verified by checking the records loaded into the destination tables and confirming that no connection, transformation, or referential-integrity errors occurred.

## 10. Process Completion and Validation

After loading the dimensions and fact table, the script closes the database connection resources and displays a completion message.

The expected result is an updated technical data warehouse containing the processed audit records, ready for subsequent multidimensional analysis and OLAP queries.

Final validation should include:

- Checking the number of records loaded into each destination table.
- Verifying that fact records reference existing dimension keys.
- Checking for duplicate records according to the defined record key.
- Confirming that the ETL completed without errors.
- Comparing source and destination counts where appropriate.
